## 코드 버그가 아닌 실제 발견 사항

- **Playwright 작동성 재시도 관련 특이 현상**: `onClick` 핸들러가 동기적으로 `busy=true`를
  설정(자기 자신을 비활성화)하는 "제출" 버튼이 Playwright 자체의 `.click()` 재시도 루프를
  혼란시킵니다 — 최초 클릭 디스패치는 실제로 성공하고 실제 요청도 전송되지만, Playwright는
  자신의 디스패치 직후 버튼이 비활성화되는 것을 "클릭이 먹히지 않았다"고 해석해, 실제로는 이미
  작업이 진행되었음에도 전체 타임아웃 동안 의미 없이 재시도합니다. 스크린샷 스크립트에서
  Playwright 자체의 작동성 재확인을 건너뛰는 `{ force: true }`로 수정했습니다.
- **더 심각한 대기 조건 함정**: `page.waitForResponse()`는 응답의 **본문**이 끝날 때가 아니라
  **헤더**가 도착하는 시점에 resolve됩니다 — 실제 `StreamingResponse`인 `/api/research/query`의
  경우, 모델이 실제로 생성을 끝내거나 클라이언트가 종료 `done` 이벤트를 처리하기 한참 전인,
  거의 즉각적인 시점입니다. 위의 작동성 특이 현상과 결합해, 실제로 혼란스러운 실패 연쇄가
  발생했습니다: 첫 번째 쿼리의 스크린샷이 (답변이 렌더링된 뒤가 아니라) 헤더가 도착한 직후에
  찍혀 "No research yet in this thread"를 보여주었고, 같은 스크립트의 *두 번째* 쿼리는 백그라운드에서
  첫 번째 쿼리의 `busy` 플래그가 여전히 `true`였기 때문에 조용히 무시되었으며, 전송된 적 없는
  요청을 기다리다 두 번째 `waitForResponse`가 타임아웃되었습니다. 수정 방법은 스트리밍
  엔드포인트에 대한 네트워크 수준의 대리 신호 대신, 실제 UI 완료 신호(렌더링된 "Groundedness"
  배지)를 기다리는 것이었습니다. 이는 이 프로젝트 시리즈 전체의 이전 모든 주차 스크린샷
  스크립트에서 형태만 달리 하며 반복해서 나타난, 스트리밍 응답의 실제 완료와 실제로 상관관계가
  없는 네트워크/DOM 신호라는 동일한 유형의 함정입니다.
