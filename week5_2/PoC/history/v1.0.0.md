## The six real bugs found and fixed this build

See `../debug/README.md` for full write-ups. Two (issue-01) were found via research and corrected
proactively before ever shipping; four (issue-02 through -06, minus -01) were found via manual
(Playwright) browser testing and direct API/audit-log inspection — not automated E2E, since none of
them were the kind of defect a pass/fail HTTP-status check could surface:

1. **A naive guardrail check order is wrong** (cost cap before permission) —
   corrected from the start, never shipped here, regression-tested against the exact
   scenario that would trigger the mislabeling.
2. **A stale "thinking" box after live completion, and a duplicated answer on reopening a past
   run** — both traced to the same root cause (the Final Answer step never emits a `step_complete`
   event) and fixed together.
3. **A run abandoned mid-stream (client disconnect) stayed `RUNNING` forever** — fixed with a lazy
   180-second staleness reaper; required also fixing `AgentRun.updated_at` to actually advance on
   updates (`onupdate=utcnow`), which it never had before.
4. **The same completed run showed different step numbers live vs. reopened** — the live view
   invented its own per-card counter instead of the backend's real per-cycle `step_count`, which the
   backend's `step_complete` events never even sent. Found by visually comparing two of this build's
   own screenshots side by side.
5. **The E2E suite's own regression test polluted the real admin account** — its synthetic "stale
   run" always attached to whichever user had the lowest id (always the seeded admin), not the
   suite's own disposable test user. Found by noticing the Dashboard's "Agent runs" count was
   nonzero on a container that should have had zero.
6. **The audit trail's own `latency_ms` column was hardcoded to `0.0` everywhere** — the "how long
   did this take" field existed at the model, API, and TypeScript-interface level, but no code path
   anywhere ever measured a real value for it. Found while trying to pull a real escalation-latency
   number for this very document.

## Three non-bug findings in the screenshot-testing tooling itself

Documented transparently (not fabricated as product bugs) in `../debug/README.md`:
- `text=/Final Answer/` resolved on the model's own raw streaming text mid-generation, well before
  real completion — the premature navigation this caused is what led directly to discovering bug 3
  above.
- `getByRole('button', {name: 'Approve', exact: true})` matched nothing — the real accessible name
  is "✓ Approve" (a checkmark prefix in the JSX).
- The replacement wait condition ("the Run button re-enables") was itself invalid, not just
  imprecise: the button's `disabled={busy || !question.trim()}` stays permanently true once
  `send()` clears the input field, independent of whether the run actually finished. A direct 56-
  second poll of the button's own `disabled` property confirmed this — it read `true` throughout,
  while the page's own rendered text simultaneously showed a fully correct completed answer.
  Separately, `page.waitForFunction(fn, {timeout})` was passing `{timeout}` as the function's `arg`
  parameter instead of `options`, silently falling back to Playwright's default 30s timeout. Fixed
  by waiting on the same status-badge text already proven reliable elsewhere in the script.
