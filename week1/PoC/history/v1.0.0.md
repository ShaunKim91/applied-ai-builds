# v1.0.0 — Initial build (CommerceIQ, PoC)

**Date**: 2026-08-24
**Built by**: Claude Sonnet 5, in a single continuous session, using this repository's own `api_keys/openrouter.md` for the OpenRouter validation.
**Environment**: macOS (Apple M4 Max, 36GB RAM, no NVIDIA GPU), Docker Desktop 29.1.5 / Compose v5 — matches the project's "no GPU, CPU is the default path" assumption exactly.

## What was built

- FastAPI backend (`backend/app/`) with 7 route modules (auth, vision, generate, forecast, search, admin, health), SQLAlchemy ORM (5 tables), a Chroma-backed vector store with a pure-Python fallback, JWT+bcrypt auth, an in-process background job manager, and 5 AI models wired in (4 local, 1 optional cloud via OpenRouter).
- React + TypeScript + Vite + Tailwind frontend (`frontend/src/`), 7 pages, bilingual (EN default / KO toggle), light default / dark toggle, a hand-built Recharts forecast chart (history + forecast + 95% CI band + anomaly markers) following the dataviz-skill validated palette.
- Docker: multi-stage build (Node build stage → Python-only runtime), `docker-compose.yml` with named volumes for data/model-cache persistence and a read-only mount of the repo's `api_keys/` directory, auto free-port detection (`scripts/find_free_port.sh`), and convenience scripts (`setup.sh`/`run.sh`/`stop.sh`/`download_data.sh`/`verify_e2e.sh`).
- Two public datasets wired to auto-download on first boot (UCI Online Retail, GroceryStoreDataset samples), both cited with license/source in `data/SOURCES.md`.
- Full documentation set: `README.md`, `architecture.md` (4 Mermaid diagrams + production-scaling table + cost estimate), `flowchart.md` (7 Mermaid flowcharts), `docs/guide.html` (bilingual, themeable, all-in-one operations guide with embedded screenshots), plus this project's `debug/`, `plan/`, `history/`, `prompts/`, `etc/` folders.

## Real issues found and fixed during this build

All five are documented in full in `../debug/`, with root cause, fix, and (where relevant) course-material pointers. Summary:

1. **chromadb/posthog telemetry error** — cosmetic, no functional impact (upstream dependency skew).
2. **Admin login was impossible** — `EmailStr`'s deliverability check rejected the `.local` TLD used for the demo admin account. **Fixed**: replaced with a shape-only email validator appropriate for an internal-tool login field.
3. **Feature timeouts on first boot** looked like bugs but were slow cold-start model downloads on this build's network (~0.6–1.5 MB/s observed) racing against test timeouts. **Fixed properly**: added a real readiness endpoint (`GET /api/health/ready`) and a wait-for-warm step in the E2E script, decoupling "download finished" from "feature works."
4. **Rebuilds intermittently missed Docker's layer cache**, re-downloading ~1GB of packages. Root-caused (with an honest dead-end documented) to likely build-cache GC pressure on this shared dev machine, not a project bug — rebuild speed only, never correctness.
5. **MAPE reported as 131,574.8%** on a real forecast run — a genuine bug: this retailer has real $0-revenue Saturdays in the data, and the naive divide-by-zero guard turned that into a nonsensical percentage. **Fixed**: MAPE now excludes near-zero-actual backtest days (with a note explaining how many), and a new sMAPE metric (bounded 0–200%) was added as an always-defined companion — the LLM insight prompt now cites sMAPE to avoid repeating a misleading number.
6. **One failed dataset download silently skipped warming all 4 AI models** — found during this build's own final clean-reproducibility test (fresh `docker compose down -v` + `docker rmi` + `scripts/setup.sh`): a transient DNS blip fetching the UCI dataset took down model warm-up too, because both were inside one shared `try/except`. **Fixed**: each of the 6 startup steps (2 datasets + 4 models) now runs in its own isolated try/except, so an unrelated step's failure can never cascade.

Also manually verified beyond the automated suite:
- **OpenRouter path** (`qwen/qwen3-8b`), called directly with the repo's real key: responded correctly ("Hello! I am Qwen.") in a smoke test, and end-to-end through the full forecast pipeline in Korean in 6.9s, producing a fluent, numerically-grounded Korean business insight.
- **All 20 GroceryStoreDataset sample images** classified via the real ViT-tiny model (not mocked) — genuine ImageNet classes matched correctly for items ImageNet actually has a class for (banana → "banana", Granny Smith apple → "Granny Smith", bell pepper → "bell pepper", lemon → "lemon"); packaged goods without an exact ImageNet class (milk cartons, yogurt) fell back to plausible-but-wrong generic labels — expected behavior for a 1000-class, non-retail-fine-tuned classifier, documented in `docs/guide.html`'s limitations section, not a bug.
- **Admin authorization boundary**: confirmed a regular user gets 403 on every `/api/admin/*` route, and the seeded admin account can read them, via both the automated suite and manual testing.

| Diffusion generation latency (warm, 4-12 steps) | 12–22s (CPU) |
| Forecast + local LLM insight latency (warm) | 14.5–17.7s |
| Forecast + OpenRouter insight latency (warm) | 6.9s (network-bound, not compute-bound) |
| Semantic search latency (warm) | <100ms |

**Cold-start note**: on this build's network (~0.6–1.5 MB/s observed, unusually slow for the dev environment), first-boot model+dataset download took approximately 15–20 minutes for the full ~3.5GB across 4 models + 2 datasets, run concurrently across the bootstrap thread and the first user request's own lazy-load. On a typical broadband connection this should be single-digit minutes; the app remains fully usable during this window (each feature simply waits on its own model's load, exactly once).

## Screenshots

Captured via Playwright (headless Chromium) driving the actual running app end-to-end (real signup, real classification, real generation, real forecast, real search, real admin login) — see `docs/screenshots/`. No screen was staged or faked; every number and image visible in the screenshots came from a real API response during capture.

One data-quality adjustment along the way, noted for transparency: the first capture pass reused a demo image that had already been classified many times across earlier manual/E2E testing, so the Semantic Search screenshot mostly showed duplicate "vending machine" entries — technically correct (real vectors, real ranking) but a poor demonstration of the feature. Fix: wiped the SQLite DB + Chroma collection (model caches untouched — no re-download needed) and classified each of the 20 sample images exactly once before the final capture, producing a genuinely diverse demo catalog. ## Reproducibility

- `scripts/setup.sh` was run from a completely clean state (no prior image, no prior volumes) at the *start* of this build and completed successfully end-to-end (build → start → healthy).
- Several subsequent rebuilds (after code fixes) were also verified end-to-end via `docker compose build && docker compose up -d` + a full `verify_e2e.sh` pass each time.
- **Final definitive check**, done last, against what was then the fully-fixed codebase: `docker compose down -v` (removes the container, network, AND both named volumes) + `docker rmi commerceiq:latest` + a fresh `rm -f .port .env` — the closest reproducible approximation of "a newcomer's first `git clone`" available in this environment — followed by `./scripts/setup.sh` with no other manual steps. **This is exactly the run that surfaced issue-06**: a genuine transient DNS failure fetching the UCI dataset took down all 4 AI models' warm-up with it (the bug, at that point still present). The fix (`debug/issue-06`) was applied immediately after, and a follow-up rebuild (`docker compose build && up -d`, reusing the same now-partially-populated volumes rather than a second full teardown) completed cleanly — datasets and all 4 models warmed with zero step errors, and the full 12-step `verify_e2e.sh` suite passed. **Being precise**: the follow-up run did not reproduce a second live DNS failure to prove the isolation fix under the exact original conditions — see `debug/issue-06`'s Verification section for what was and wasn't directly observed. What IS fully proven end-to-end: a true zero-state clean rebuild (`setup.sh` from nothing) works, and the specific bug that run exposed was root-caused and fixed.
