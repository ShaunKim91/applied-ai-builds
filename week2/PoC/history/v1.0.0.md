# History — v1.0.0 (2026-08-28)

The original build of VoxIQ (Week2 PoC): plan approval → scaffolding →
backend → frontend → containerization → live verification → clean-rebuild
reproducibility test → documentation, all in one continuous session,
directly following the same methodology as the Week1 PoC ("CommerceIQ").

## What was built

6 AI models across 4 features tied into one "AI meeting & knowledge
intelligence" product, plus auth and an admin console — see `../README.md`
for the feature list and `../architecture.md` for the full design. Scope
matched the approved plan (`../plan/v1_plan.md`) with no scope creep.

| Step | Elapsed |

| Bi-encoder + cross-encoder load (`all-MiniLM-L6-v2`, `ms-marco-MiniLM-L-6-v2`) | 26 s |

| Tokenizer explorer load + first-time download (`gpt2`, ~500 MB) | 60 s |

This is a genuine cold-start measurement: the named volumes were deleted
immediately beforehand (see "Clean reproducibility"), so all 5 models and

populated (e.g. `./scripts/run.sh` after the first successful boot) skips
all of the above — the models load from the local cache in a few seconds.

## Real issues found (2, both documented in `../debug/`)

1. **`setup.sh` printed "4 local AI models"** (VoxIQ has 5) — a leftover
   literal from copy-adapting CommerceIQ's script. Cosmetic only, fixed.
2. **The local LLM (Qwen2.5-0.5B) reliably generated code that crashed**
   with `ValueError: too many values to unpack` on a specific request,
   because the system prompt described the data's shape but not how to
   iterate it safely; the larger OpenRouter model didn't make the same
   mistake on the same request. Fixed with a more explicit prompt (anti-
   example + correct-usage example); re-verified 3/3 correct afterward,
   plus a full `verify_e2e.sh` re-run (still 12/12).

Notably fewer issues than Week1's 7 — see `../debug/README.md` for why:
VoxIQ deliberately started from CommerceIQ's already-hardened scaffolding
rather than rebuilding auth/bootstrap/readiness patterns from scratch.

## Clean reproducibility (measured, genuine zero-state test)

```
docker compose down -v        # removed the voxiq container + both named volumes
docker rmi voxiq:latest       # removed the image tag (build cache itself persisted,
                               # which is expected/correct BuildKit behavior — see note below)
./scripts/setup.sh            # fresh build + up, from an empty image tag + empty volumes
```

Result: image rebuilt (build-cache hits meant this step took under a
minute; the *volumes* — the part that actually matters for "does this
redownload cleanly" — were genuinely empty), container started, all 5
models + both datasets downloaded from scratch in 274 s (see timing table
above), and `verify_e2e.sh` passed 12/12 again immediately afterward with
no manual intervention.

Note on the image-rebuild speed: `docker rmi` removes a *tag*, not
BuildKit's underlying layer cache — a near-instant "all CACHED" rebuild
after removing the tag is correct, expected Docker behavior, not a sign the
test was skipped. The part of this test that actually exercises "does
first-boot work from nothing" is the named-volume wipe (`-v`), which was
real and is what produced the from-scratch download timing above.

## API-key-leakage audit (real, double-method, zero hits)

Same standard the user required for Week1, re-run against the complete
`week2/PoC/` tree with the real key loaded from `api_keys/openrouter.md`:

- **Wrapped `grep -r`** (respects any `.gitignore` it finds) — 0 hits.
- **`command grep -r`** (bypasses the wrapper, ground truth) — 0 hits.
- `backend/app/config.py` — confirmed to hold only a file path
  (`openrouter_api_key_file: str = "/app/secrets/openrouter.md"`), never a
  literal key.
- `docker-compose.yml` — confirmed the mount is read-only
  (`../../../../api_keys:/app/secrets:ro`), no key baked into any build arg
  or environment variable.
- The repo-root `.gitignore` added during the Week1 follow-up
  (`/Users/.../.gitignore`) already covers `api_keys/`
  for every product in this series, including this one — nothing new needed here.

One screenshot-process note, not an application bug: the first dashboard
capture raced ahead of two of its own `useEffect` API calls (a Playwright

Recaptured with an explicit wait on those two response promises; direct
`curl` calls against the same endpoints confirmed they were always correct
and fast (`/api/search/status` responded in well under 100 ms).
