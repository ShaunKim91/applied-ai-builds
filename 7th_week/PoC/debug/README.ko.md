## 코드 버그가 아닌 실제 발견 사항

- **스크린샷 스크립트의 대기 조건(`text=/Final Answer/`)이 진짜 완료가 아니라 모델 자체의 원시
  스트리밍 텍스트가 생성되는 도중에 resolve됨** — 이것이 이슈 03을 발견하게 된 계기였습니다
  (스크립트의 이른 페이지 이동이, 실제 사용자가 응답 도중 탭을 닫을 때와 정확히 같은 방치
  시나리오를 재현했습니다). 이 취약점 자체는 실재했으며, 대기 조건은 사람이 알아챘을 때보다
  더 일찍 그것을 발견했을 뿐입니다. `prompts/vibe_coding_prompts.md` 참고.
- **두 번째, 별개의 셀렉터 정밀도 함정**: `getByRole('button', {name: 'Approve', exact: true})`가
  아무것도 매칭하지 못했는데, 실제 접근성 이름에 체크마크 접두사("✓ Approve")가 포함되어
  있었기 때문입니다. 잘못된 버그 리포트가 나오기 전에 수정했습니다.
- **세 번째, 처음엔 제품 버그일 수도 있다고 오해했던 셀렉터/API 사용 함정**: Final-Answer
  부분 문자열 대기를 고친 뒤 대체 조건으로 쓴 "Run 버튼이 다시 활성화되길 기다림" 자체가
  부정확한 게 아니라 아예 무효였습니다. Playwright의 특이 현상 때문에 실패한 게 아니라,
  버튼의 `disabled={busy || !question.trim()}`가 `send()`가 입력 필드를 비운 순간부터
  `busy` 값과 무관하게 영구적으로 `true`로 유지되었기 때문입니다. `button.isDisabled()`를
  직접 폴링하면 56초 내내 매 체크포인트마다 `true`가 나왔지만, 같은 시간에 페이지에 렌더링된
  텍스트는 완전히 올바른 완료된 답변을 이미 보여주고 있었습니다 — 신호 자체가 잘못되었지
  느린 게 아니었다는 증거입니다. 별도로, `page.waitForFunction(fn, {timeout})`은 `{timeout}`을
  함수의 `arg` 매개변수로 전달하고 있었고 `options`로 전달하지 않았습니다(올바른 3개 인자
  형태는 `page.waitForFunction(fn, null, {timeout})`입니다), 그래서 Playwright의 기본
  30초 타임아웃으로 조용히 폴백되었습니다 — 첫 번째 실수 위에 겹쳐진 두 번째 독립적인
  실수였습니다. 스크립트의 다른 곳에서 이미 신뢰성이 입증된 동일한 상태 배지 텍스트를
  기다리는 방식으로 수정했고, 버튼 상태 기반 접근은 완전히 버렸습니다.
