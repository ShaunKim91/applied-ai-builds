연결합니다.

## 이번 빌드가 처음부터 올바르게 물려받은 것 (재발견이 아님)

전작인 Cradle PoC와 달리, 이번 빌드는 Cradle 자체의 실제 버그 6건 중 어느 것도 재현하지 않았습니다 —
각 교훈을 코드 첫 줄부터 선제적으로 적용했을 뿐, 다시 발견한 게 아닙니다:

- **올바르게 수정된 안전장치 검사 순서**(스텝 한도 → 권한 → 비용 상한 → HITL) — 처음부터
  올바르게 구현되었으며, 이런 패턴의 일반적인 구현에서 흔히 나타나는 안전장치 순서 버그
  시나리오를 그대로 재현하는 직접적인 회귀 테스트(`step_guardrail_order_regression`)를
  갖추고 있습니다.
- **오래된 실행 정리 로직**(`_reap_stale_runs()`)과 그것이 의존하는 `AgentRun.updated_at`의
  `onupdate=utcnow` 수정 — 둘 다 첫 커밋부터 존재했으며, 실제로 실패가 나타나는 것을 기다리는
  대신 직접적인 회귀 테스트(`step_stale_run_reaper_regression`)를 갖추고 있습니다.
- **실시간 스트리밍 실행과 다시 연 실행 간의 일관된 스텝 번호** — `step_complete` 이벤트가
  처음부터 실제 백엔드의 `step_count`를 포함해, Cradle이 겪고 나중에 고친 실시간-vs-재열람
  불일치를 애초에 피했습니다.
- **Final Answer 단계의 `streamingText` 초기화**와 **재열람 시 `final_answer` 종류 스텝
  필터링** — 둘 다 `Console.tsx`의 최초 버전부터 존재했습니다.

이번 라운드에서 진짜로 새로 발견된 실패 유형은 단 하나뿐이었고, 이는 Cradle이 겪을 기회조차
없었던 것이었습니다: Cradle의 도구 인자는 순수하게 숫자이거나 단순한 쉼표 구분 쌍이었을
뿐이라, 그 빌드 자체의 테스트 중에는 모델이 굳이 따옴표를 사용할 이유가 없었습니다. Threshold의
더 풍부한, 문자열 중심적인 도구 세트(키워드로 절차를 조회)는 모델이 따옴표로 감싸는 문법을
사용할 이유를 더 많이 만들어, 어떤 특정 빌드가 먼저 발견했는지와 무관하게 파서가 처리해야 하는
실제 공백을 드러냈습니다.

## 제품 버그가 아닌 실제 발견 사항

위 수정을 반복 작업하는 동안, 같은 장수명 컨테이너(시도 사이에 이미지는 재빌드하되 볼륨은
재빌드하지 않음)를 대상으로 `verify_e2e.sh`를 연속으로 여러 번 재실행하다 보니, 이미 스위트
자체의 앞선 스텝이 성공적으로 사용했던 도구에 대해 뜬금없이 `BLOCKED_PERMISSION`이 발생하는
실행이 나왔고, 이어서 이후 여러 인증 관련 스텝에서 연쇄적인 `429 Too Many Requests` 오류가
발생했습니다. 이는 예상된 동작이며 버그가 아닙니다: 레이트 리미터(`rate_limit.py`)와 안전장치
설정 모두 같은 컨테이너의 프로세스/데이터베이스에 걸쳐 반복 호출 사이에도 유지되는 실제
영속 상태이며, 인증이 많은 스위트를 자체 60초 레이트 리밋 윈도우 안에서 여러 번 실행하면
정상적으로 이를 소진시킵니다 — 설계된 그대로입니다. 완전한 클린 재빌드(`docker compose down
-v`)로 전부 초기화하자 바로 다음 시도에서 동일한 26/26 스위트가 깔끔하게 통과했고, 이는 레이트
리미터나 안전장치 영속성 자체의 결함이 아니라 이번 디버깅 세션의 테스트 진행 방식에서 비롯된
아티팩트였음을 확인해 주었습니다.
