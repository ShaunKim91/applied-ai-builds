# History — v1.0.0 (2026-08-29)

The original build of Parchment (Week3 PoC): plan approval → scaffolding →
backend → frontend (with a genuinely new design-token pass, per this
round's explicit UI-differentiation request) → containerization → live
verification (2 real bugs found and fixed) → clean-rebuild reproducibility
test → documentation, all in one continuous session, following the same

## What was built

6 AI models across 3 features tied into one "document intake desk"
product, plus a duplicate-detection library, auth, and an admin console —
see `../README.md` for the feature list and `../architecture.md` for the
full design. Scope matched the approved plan (`../plan/v1_plan.md`) with no
scope creep. This build also carries the session's most substantial visual
redesign to date: a warm parchment/terracotta palette, serif (Newsreader)
headings, and a top-tab layout, replacing the Week1/2 PoCs' identical
cool-gray sidebar dashboard look (verified via a direct diff of their
`tailwind.config.js`/`index.css` before this build started).

## Bootstrap timing (measured, clean-rebuild run — see "Clean reproducibility" below)

This session's model downloads ran markedly slower throughout than the
Week1/2 PoCs' builds earlier in the same overall project — a genuine,
observed characteristic of this specific session's network conditions, not
a code issue (confirmed by directly loading each model standalone inside
the container, outside the bootstrap thread, which succeeded quickly every
time it was tested).

| Step | Elapsed |
|---|---|
| Container start → sample documents ready (synthetic receipts + Fed PDF download) | 2s |
| Local VLM load (`SmolVLM-256M-Instruct`, ~500MB) | 4m 38s |
| Local LLM load (`Qwen2.5-0.5B-Instruct`, ~2GB) | 8m 35s |
| Summarizer load (`distilbart-cnn-12-6`, ~1.2GB) | 9m 15s |
| Embedding model load (`all-MiniLM-L6-v2`, ~90MB) | **10m 00s** |
| **Total, container start → "all sample documents + models warm"** | **≈ 32m 30s** |

The embedding model's 10-minute load time is disproportionate to its ~90MB
size (far slower, per byte, than the other four — e.g. the 2GB LLM loaded
faster in absolute terms). This exact pattern — `all-MiniLM-L6-v2`
specifically being the slowest step to register as warm — was observed
independently in **both** this build's initial cold start and this
from-scratch clean-rebuild test, despite a direct, standalone load of the
same model (outside the bootstrap thread, via `docker exec`) completing
in well under a minute both times. The most plausible explanation is a
slow/retried Hub metadata check specific to this small, frequently-mirrored
model under this session's network conditions, rather than a problem with
the model or the loading code — but this is an honest "consistently
observed, not fully root-caused" finding, not a confirmed diagnosis.
Functionally, this cost nothing beyond wall-clock time: `_warm_step()`'s
isolation meant `/api/health` and every other already-warm feature stayed
usable the entire time, which is exactly the scenario that pattern exists
to handle.

## Real issues found (2, both documented in `../debug/`)

1. **PDF summarization timed out (180s) on the real Fed report.** The
   original map-reduce implementation summarized 191 word-count chunks one
   at a time; a genuinely long real document (34,267 words) made this
   sequential approach too slow. Fixed with batched inference, larger
   chunks (220→500 words), and an explicit, surfaced cap (`MAX_CHUNKS=20`,
   evenly sampled across the document) — re-measured at **56.7s**, with a
   materially *more coherent* summary as a side effect (fewer, larger
   partial summaries combine better than many tiny fragments). See
   `../debug/issue-01-pdf-summarize-timeout-on-real-document.md`.
2. **Numeric cross-check false-flagged a real, source-backed number.**
   OpenRouter's `qwen/qwen3-8b` correctly summarized the Fed's "2 percent"
   inflation target as "2%" — a notation difference the naive exact-match
   check didn't recognize as equivalent, wrongly reporting a true, sourced
   fact as "unverified." Fixed by normalizing percent notation before
   comparing. See `../debug/issue-02-numeric-check-percent-notation-mismatch.md`.

Both were found by actually exercising the running app against the real
bundled Fed report (not a toy document) — issue 1 via the first real
`verify_e2e.sh` run, issue 2 via directly testing the OpenRouter path with
the real API key against the same document.

## OpenRouter — real key, real calls

Direct tests against the live container (not part of `verify_e2e.py`,
matching the same real-key validation done for the Week1/2 PoCs):

```
POST /api/pdfs/summarize-sample {"use_openrouter": true}
→ 200 OK, provider: openrouter, model: qwen/qwen3-8b
→ measured latency: ~7.1–7.3s (network round-trip to openrouter.ai + generation)
→ summary correctly states the Fed's 2% inflation target, federal funds
  rate context, and policy review cadence — all verified against source
  after the issue-02 fix
```

Confirms the same "local default, cloud opt-in, independently fail-safe"
pattern already used in the Week1/2 PoCs' `llm.py` works identically here
for a third feature (PDF summarization instead of a forecast narrative or
code generation).

## Clean reproducibility (measured, genuine zero-state test)

```
docker compose down -v        # removed the parchment container + both named volumes
docker rmi parchment:latest   # removed the image tag
./scripts/setup.sh            # fresh build + up, from an empty image tag + empty volumes
```

Result: image rebuilt to **2.55 GB**, container started from empty volumes,
all 5 models + sample documents downloaded from scratch in the ≈32m 30s
measured above (see the timing table), and `verify_e2e.sh` passed
**13/13** again immediately afterward with no manual intervention —
including its own internal wait-for-warm step correctly tolerating the
slow `embeddings` load (138.4s of that step's own patience budget) rather
than falsely reporting a failure.

Final measured state after the clean rebuild: `parchment_hf_cache` at
3.8 GB (5 models cached), container memory at rest ≈5.4 GiB.
