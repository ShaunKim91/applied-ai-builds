All numbers below are real measurements taken during this build session (Docker on macOS,
CPU-only, no GPU) — none are estimated or hallucinated. Where a number depends on timing, the raw
log lines it was computed from are quoted.


**Total, container start → `all_warm: true`: 12 minutes 44 seconds.**

**A genuinely observed anomaly, honestly reported, not fully root-caused**: the local LLM step took
8m 23s despite the model being only ~1GB — the same class of anomalously slow-then-fast
model-download behavior observed repeatedly in this session's Week3 and Week4 builds (a real
`curl` to huggingface.co responds in under a second; the actual weight download proceeds in uneven
bursts rather than a steady rate). This build's own earlier (pre-final-fix) cold run measured
12m53s end to end, confirming the pattern is reproducible, not a one-off fluke.

## The one real bug found and fixed this build

See `../debug/README.md` for the full write-up. Found via manual (Playwright) browser testing, not
automated E2E — the first two E2E runs happened not to trigger it, since it depended on the exact
shape of one specific real local-model generation:

1. **Trend Radar's JSON extraction failed on a real, valid model output.** `Qwen2.5-0.5B-Instruct`
   produced a syntactically-complete, correctly-shaped JSON verdict followed by one stray extra `}`
   — the original greedy regex (`\{.*\}`) swallowed that extra brace into its parse candidate,
   making `json.loads()` fail on otherwise-perfectly-valid JSON. Fixed with a brace-depth-counting
   extractor that stops at the first properly-balanced object. Re-verified against the exact
   captured malformed string (now recovers correctly) plus a prose-wrapped-clean-JSON case and a
   fully-non-JSON case (both still behave correctly) — see `docs/screenshots/05-trend-radar.png`
   for the fixed feature rendering three real lens verdicts instead of a raw-JSON error message.

## Two non-bug ambiguities found in the screenshot-testing tooling itself

Documented transparently (not fabricated as product bugs) in `../debug/README.md`: a bare
`input[placeholder]` Playwright selector matched both the Layout's global command-console input and
a page's own composer input (fixed with exact-text `getByPlaceholder`), and `button:has-text
("Search")` also substring-matched any button labeled "**re-search**" — e.g. the sidebar's "New
research" button. Both were caught and fixed before they could produce a false bug report.

## Real findings that are not code bugs

- **The local 0.5B model does not always include inline `[n]` citation markers**, even though the
  system prompt asks for one per claim — observed directly in `docs/screenshots/02-research.png`. A
  known instruction-following limitation of very small local models, not a defect in the
  citation/groundedness-checking code (which correctly still passes such an answer when its content
  is genuinely accurate, since there's nothing invalid to flag).
